# Test Execution Report Template

**New here? Read `START_HERE.txt` first** — it's the fastest path to
seeing a real report, and explains why the files in `template/` (the
`.html.j2` ones) shouldn't be opened directly.

Turns a test case library + execution results into a self-contained HTML
report — for any project, not just one. Two report types, both light/dark
aware with badge-based statuses and sticky/scrollable tables:

- **lite** — the compact pass/fail/skip dashboard with live search +
  filters, plus three optional cards that only appear when you give them
  data: **Human Action Required** (test cases that couldn't be
  automated and need a manual approach), **Investigation / Evidence-
  Gathering Results** (evidence gathered where there's no clean
  pass/fail oracle yet — these never count as a Pass), and **Open Gaps
  / Limitations** (a plain record of what wasn't fully covered, no
  resolution-owner tracking baked in). This is the one to reach for by
  default — a bare run with none of those three files looks exactly
  like the original dashboard.
- **full** — a heavier, more document-like layout (header meta grid,
  status banner, executive summary, Blocked/Not-Run analysis, Evidence
  Appendix, and more) for when a report needs to stand alone as a
  formal stakeholder-facing record. Available if you need it, but
  `lite` is the better starting point for most runs.

## Files

```
template/
  test_execution_report.html.j2        the lite template
  test_execution_report_full.html.j2   the full template
generate_report.py                     reads a config + your data, renders one of the above
sample-data/
  lite/   worked example for --report-type lite
  full/   worked example for --report-type full
```

Both templates are visual/layout only — no project-specific content in
either. Don't edit them unless you want to change the report's structure
or styling for every future project.

## Quick start

```bash
pip install jinja2 --break-system-packages   # if not already installed
python3 generate_report.py --config sample-data/lite/report_config.json
python3 generate_report.py --config sample-data/full/report_config.json
```

Each writes to the `output_path` its config names (defaults to
`generated/`). Open the resulting HTML file directly — no server needed.

## Using it for a real project

1. Copy `sample-data/lite/` or `sample-data/full/` to a new folder.
2. Edit `report_config.json` (schemas below).
3. Replace the data files under `data/` with your project's data — hand
   -written, or generated by whatever your pytest/Playwright run already
   produces (a `conftest.py` hook or a post-run script is the natural
   place to write these).
4. Run `python3 generate_report.py --config <your-folder>/report_config.json`.

Re-run any time you have fresh results — the report always reflects
whatever's currently in the data files. `--report-type`, `--output` on
the command line override the corresponding config fields for a one-off
run without editing the file.

## Lite schema

### `report_config.json`

| Field | Required | Meaning |
|---|---|---|
| `report_type` | no (default `lite`) | `"lite"` |
| `project_name` | yes | Page title / `<h1>`. |
| `system_label` | yes | First clause of the subtitle. |
| `run_context` | no | Trailing clause of the subtitle, e.g. `"after the last pytest run"`. |
| `scope_label` | no | Optional parenthetical after the count in the Summary heading. |
| `timezone` | no (default `UTC`) | IANA name; used for `generated_at` and shown in the subtitle. |
| `timezone_short` | no | Short label in the "Last executed" column header, e.g. `"KL"`. |
| `generated_at` | no | Override the auto-computed timestamp. |
| `library_path` / `results_path` | yes | Paths to the two data files below, relative to the config file (or absolute). Also shown verbatim in the subtitle's "source:" line. |
| `output_path` | no | Where to write the report (default `test_execution_report.html`). |

### `test_case_library.json` — list of `{id, module, title, priority}`

### `last_execution_results.json` — list of, per case that ran:

```json
{ "id": "TC-1", "status": "fail", "last_executed": "2026-09-15T09:12:31+08:00",
  "duration_seconds": 12.07, "evidence": "evidence/TC-1.png", "notes": "..." }
```

- `status`: `pass` | `fail` | `blocked-env` | `skipped` | `not-run`. A
  library entry with no matching result is automatically `not-run` — you
  don't need to enumerate every not-yet-run case, just omit it.
- `duration_seconds`: `0` renders `0.0s`; omitted/`null` renders `—`.
- `evidence`: relative path/URL, rendered as a "screenshot" link; `null` → `—`.

Everything on the Summary card and the Coverage-by-module table is
computed from these two files — you never hand-tally counts or percentages.

### Optional cards (lite)

Add any of these to `report_config.json` to turn on the matching card.
Leave a field out and that card doesn't render at all — no empty
placeholder, the report just looks like the bare 3-card dashboard.

| Field | Card | Data shape |
|---|---|---|
| `human_action_path` | Human Action Required | list of `{id, module, title, reason, recommended_handling}` — `id` is optional, use it if the item corresponds to a test case in your library. |
| `investigation_path` | Investigation / Evidence-Gathering Results | list of `{id, objective, outcome, observation, evidence, gap_ref, notes}` — same shape as full mode's. |
| `gaps_path` | Open Gaps / Limitations | list of `{id, status, description, impact}` — no resolution-owner field; this is a plain record of what was and wasn't covered, not a tracked-to-resolution register. `status` is free text, colored by a best-effort keyword classifier (open/blocked→red, pending/in-progress→amber, resolved/closed→green, else neutral). |

`gap_ref` in `investigation_items.json` renders as a jump-link to the
matching row in Open Gaps when the id matches; otherwise it's shown as
plain text.

```bash
python3 generate_report.py --config sample-data/lite/report_config.json
```

`sample-data/lite/` has all three wired up — open the rendered output to
see the full 6-card layout, or strip the three `*_path` fields out of
`report_config.json` to see it fall back to the bare 3-card version.

## Full schema

### `report_config.json`

All the lite fields above **except** `system_label`/`scope_label`/
`run_context`/`timezone_short`, replaced by:

| Field | Required | Meaning |
|---|---|---|
| `report_type` | yes | `"full"` |
| `scope` | no | Subtitle line under the project name. |
| `execution_id` | no | Shown in the header meta grid. |
| `environment` | no | e.g. `"UAT"`, `"Staging"`. |
| `automation_framework` | no | e.g. `"Playwright + pytest"`. |
| `overall_status` | no (default `"Completed"`) | Free text; colors the status banner via keyword match (`fail`→red, `block`→purple, `partial`/`limited`→amber, `pass`/`complete`/`success`→green). |
| `sut_reached` | no | Free text ("Yes"/"No"/"Partially"...). Defaults to `"Yes"` if any test case produced a Pass or Fail verdict, else `"No"`. |
| `executive_summary_text` | no | Freeform paragraph under the metrics grid. |
| `library_path` / `results_path` | yes | Same as lite, but see the extended shapes below. |
| `human_action_path` | no | Path to `human_action_items.json`. Omit for "no items" (renders an empty-state row, not an error). |
| `investigation_path` | no | Path to `investigation_items.json`. |
| `blocked_notrun_path` | no | Path to `blocked_notrun_items.json`. |
| `gaps_path` | no | Path to `gaps.json`. |
| `followups_path` | no | Path to `followups.json` (a plain list of strings). |
| `preflight_path` | no | Path to `preflight_checks.json`. |
| `runtime_and_command` / `runtime_and_command_path` | no | Inline string, or a path to a text file — pick one. |
| `raw_execution_logs` / `raw_execution_logs_path` | no | Same choice, for the raw-logs panel. |
| `generated_by` | no (default `"Test Executor"`) | Credited in the footer disclaimer. |
| `output_path` | no | Default `test_execution_report_full.html`. |

Every `*_path` field above is optional — leave it out and that section
renders a one-line "nothing recorded" placeholder rather than an empty
table with just headers. Nothing forces you to populate a governance
section a given run doesn't need.

### `test_case_library.json` — list of:

```json
{ "id": "TC-CHK-PAY-002", "module": "Payments", "scenario": "Declined card shows retry prompt",
  "priority": "High", "expected_result": "A retry prompt with the decline reason appears" }
```

### `execution_results.json` — list of, per case that ran:

```json
{ "id": "TC-CHK-PAY-002", "status": "fail",
  "actual_result": "No retry prompt appeared; order silently stayed Pending",
  "evidence": "evidence/TC-CHK-PAY-002.png", "verified_by": "Cherlynn Ng",
  "last_executed": "2026-09-15T09:12:31+08:00", "gap_ref": "GAP-001",
  "notes": "AssertionError: expected retry prompt, none shown" }
```

- `status`: `pass` | `fail` | `blocked` | `not-run` | `not-verified`.
  Omitted from a library entry → automatically `not-run`.
- `gap_ref`: a gap's `id` (see `gaps.json`) — if it matches, the cell
  renders as a jump link to that gap's row; otherwise shown as plain text.

Pass/Fail are the only **trustworthy verdicts**: `Execution Coverage`
= Trustworthy Verdicts ÷ all cases, `Pass Rate` = Pass ÷ Trustworthy
Verdicts. Blocked/Not-Run/Not-Verified aren't judgments about the
software, so they're excluded from Pass Rate but still counted in
coverage's denominator, at both the report level and per-module in
Coverage by Module.

### `human_action_items.json`

```json
{ "severity": "Critical", "category": "Environment", "issue": "Sandbox FX rate feed unavailable",
  "impact": "Blocks all currency-conversion cases", "required_action": "Restore or mock the feed",
  "owner": "DevOps", "status": "Open" }
```

`severity` and `status` are free text, colored by a small keyword
classifier (severity: critical/blocker/high→red, medium→amber, else
neutral; status: open/blocked/overdue→red, in-progress/pending→amber,
resolved/closed/done→green, else neutral). Word your values naturally —
the classifier is best-effort, not an enum you have to match exactly.

### `investigation_items.json`

```json
{ "id": "INV-001", "objective": "...", "outcome": "Inconclusive — needs a backend timer check",
  "observation": "...", "evidence": "evidence/INV-001.png", "gap_ref": "GAP-002", "notes": "..." }
```

`outcome` is shown as plain text (not badge-colored) — investigation
outcomes are usually too qualitative to reduce to a good/bad color.

### `blocked_notrun_items.json`

```json
{ "item": "TC-CHK-PAY-004 (Currency conversion rounding)", "status": "Blocked",
  "reason": "Sandbox FX rate feed unavailable", "affected_scope": "1 test case in Payments",
  "required_condition": "FX feed restored or a mock rate service is provided" }
```

This is a curated register explaining *why* and *what resumes it* — not
a duplicate of every blocked/not-run row already visible in Verification
Results.

### `gaps.json`

```json
{ "id": "GAP-001", "status": "Open", "description": "No retry prompt on declined card payment",
  "impact": "Merchants may retry blindly or abandon checkout", "resolution_owner": "Dev Team" }
```

`id` is what `gap_ref` fields elsewhere point at for the jump-link.

### `followups.json` — a plain list of strings, rendered as bullet points.

### `preflight_checks.json`

```json
{ "check": "FX rate feed", "status": "Failed", "detail": "GET /fx/rates timed out after 10s — see GAP-003" }
```

## Notes on fidelity

The lite template was reverse-engineered from an existing auto-generated
report and checked row-for-row (183 test cases, every summary stat, every
coverage row) against the original before being generalized. Its three
optional cards, and the separate `full` template, were adapted from a
different, more audit-oriented template — reusing lite's own badge/color
system rather than importing that template's separate visual language,
so the result still reads as the same dashboard, not a bolted-on
document. All three variants (bare lite, lite with the optional cards,
full) were generated and structurally checked: correct section
counts/order, correct computed stats, every gap cross-link resolving to
a real anchor, every status badge carrying a real color class, and a
run with every optional file omitted rendering cleanly (bare 3-card
dashboard for lite, empty-state placeholders for full) rather than
breaking.
